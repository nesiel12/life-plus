# Atlas — Engineering Backlog

This is the living, continuously-maintained list of everything known to need doing that isn't part of the *current* roadmap phase's objectives. `docs/ARCHITECTURE_AUDIT.md`, `docs/TECH_DEBT.md`, and `docs/FEATURE_GAP_ANALYSIS.md` are the point-in-time audit that started this process — they stay as-written, a historical snapshot. This document supersedes them going forward as the place new findings get filed and old ones get closed. `docs/ATLAS_ARCHITECTURE_VISION.md` is the long-term target architecture this backlog's items get checked against — read it for *why* something here is sequenced the way it is.

**Rule:** discovering something while working on a phase does not interrupt the phase unless it makes the app unstable, insecure, or fundamentally incorrect *right now*. Otherwise, it gets a row here and gets picked up when its priority comes due.

Each entry: what it is, why it's at that priority, where it lives, and what it depends on (if anything). Closed items are removed, not struck through — git history is the record of what used to be here.

## High Priority
*Architectural improvements that should land before any real user besides the current one touches this.*

- **RLS policies are fail-closed placeholders, not active protection for the current access path.** Every table has RLS enabled with zero policies, which blocks the anon/authenticated keys entirely — but the app talks to Postgres via the service-role key, which bypasses RLS by design. The actual tenant-isolation boundary today is disciplined `user_id` filtering in `lib/db/*.ts` (verified live — see `scripts/verify-phase1.mjs`), not RLS. This is documented in the migration file; flagged here so it doesn't get mistaken for protection it doesn't provide if a future feature ever queries Supabase directly from the client. *Files: `supabase/migrations/20260720000000_init.sql`.*
- **In-memory rate limiter won't survive horizontal scaling.** `lib/api/rateLimit.ts` is correct for a single process; needs a shared store (Redis/Upstash) before Atlas ever runs more than one instance. *Files: `lib/api/rateLimit.ts`.*
- **Full end-to-end verification still pending a real browser session.** Phase 1's CRUD/isolation checks were run directly against the database (`scripts/verify-phase1.mjs`) since a real Google sign-in can't be driven from here — that proves the data layer is correct, but the actual click-through (sign in → hydrate → mutate → see it persist) hasn't been observed in a live browser yet.

## Medium Priority
*Quality, refactors, UX consistency, maintainability.*

- **No pagination anywhere a list renders** (`moments`, `goals`, `people`, and now the unified Timeline feed built from all three plus `knowledgeEntries`). Fine at current usage levels, won't scale indefinitely — Timeline Experience v1 makes this marginally more relevant (one screen, four merged sources) without making it urgent enough to solve speculatively.
- **Rate-limit thresholds are unvalidated guesses** (20/10/10 per 5 min) — reasonable defaults, not tuned against real usage. Revisit once there's real traffic to look at.
- **Test coverage is strong on pure logic, absent on DB-touching orchestration.** Vitest + CI (lint/typecheck/test on every PR) are live (`.github/workflows/ci.yml`), covering date math, `calendarFreeSlots`, `rankRelevance`, `formatContext`, every Personal DNA analyzer + confidence model, Recommendation Intelligence's feedback weighting/status-transitions/outcome summaries, Atlas Intelligence Engine's normalization/ranking/conflict-detection, Timeline Experience v1's event assembly/grouping, Goals Experience v2's stage/estimate/rationale logic, Learning Experience v2's study-streak/next-review-pick logic, Areas Experience v2's attention-level/activity-trend logic, and `chatSystemPrompt`'s ranked-signal wiring (170 tests total; also fixed a pre-existing timezone-flaky fixture in `lib/utils.test.ts` that built its dates via UTC `toISOString()` against a function that compares local calendar days). Still genuinely untested: `buildAtlasContext`, `analyzePersonalDNA`, `personalPatternsRepo`, `recommendationEventsRepo`/`createRecommendationEvent`/`recordRecommendationOutcome`, `retrieveRelevantMemory`'s DB composition, and the `app/api/goals/insights`/`app/api/torah/insights`/`app/api/areas/insights`/`app/api/chat` routes' own orchestration — all thin DB-composition layers with no automated coverage, blocked on the same "no integration-test harness yet" gap. Also open: integration tests for the API routes themselves, component tests, error tracking/structured logging.
- **Streaming moved one class of `/api/chat` failure from a clean server-side fallback to a client-side one.** `generateText` could `try/catch` a real OpenAI failure entirely before responding; `streamText` commits to a response first, so a failure *after* the stream starts surfaces mid-stream instead. `AICompanion`'s reader loop catches this and shows the same friendly error message, just one layer further out — not a regression in what the user sees, but a real, worth-tracking change in *where* the safety net sits. *Files: `app/api/chat/route.ts`, `components/layout/AICompanion.tsx`.*
- **Chat's "based on" reasoning is session-only, not persisted.** `AICompanion` keys it by the client-generated message id in local state — reloading the page or reopening the panel loses it for past replies. Deliberate (no `chat_messages` schema change for a transparency feature that doesn't need one yet), but worth naming as a real limitation, not an oversight. *Files: `components/layout/AICompanion.tsx`, `app/api/chat/route.ts`.*
- **Torah Space extraction's AI-summarized path is untested against `OPENAI_API_KEY` being live** (it's currently blank — see `docs/PROJECT_ANALYSIS.md`). The pipeline (`app/api/torah/extract`) genuinely extracts PDF text (`unpdf`) and transcribes audio (Whisper) now instead of returning fixed fake content, and was smoke-tested standalone: real PDF text extraction confirmed working, and the `generateObject` summarization call confirmed reachable (fails only on the placeholder empty key, as expected). The honest-fallback path (no key → real extracted text/snippet instead of an AI summary) is what actually runs today. Revisit once a real key is set.
- **Calendar suggestions still doesn't rank by focus window.** A confident inferred `peakActivityWindow` pattern (Personal DNA Engine v1, `docs/ATLAS_ARCHITECTURE_VISION.md` §3) now enriches a matching suggestion's *rationale* text, but the ranking itself (which life area / which slot gets suggested) is unchanged — deliberately scoped as "foundation only" this milestone. The stated (not inferred) `peakFocusHours` field remains unused entirely, same reasoning as before: free text, not structured hours. *Files: `app/api/calendar/suggestions/route.ts`.*
- **Torah page's client-side `findRelatedSessions` now duplicates server-side memory retrieval.** `app/areas/torah/page.tsx`'s keyword-overlap matcher against the *returned* topic and the server's `relevantMemory` (via Context Engine, used *during* summarization) do similar jobs from two different angles — one shows "related past sessions" in the UI, the other actually informs the AI's summary. Not urgent (both are honest, neither is broken), but worth reconciling into one mechanism once the UI-facing "related sessions" list is revisited. *Files: `app/areas/torah/page.tsx`, `app/api/torah/extract/route.ts`.*
- **`milestoneCompletionPace` (Personal DNA) has no evidence yet.** It only populates from milestones completed *after* migration `20260720000003` added `completed_at` — anything marked done before that has no timestamp, deliberately left `null` rather than backfilled with a guess. Will start producing a pattern once ~3 milestones are completed going forward. Not a bug, just a cold-start gap worth knowing about if it looks "missing." *Files: `lib/intelligence/personalDNA/analyzers/goals.ts`.*
- **Recommendation feedback doesn't adjust Personal DNA confidence yet.** `recommendation_events` now exists and is written to (calendar suggestions, goal breakdown) and read from (`getRecommendationInsights` → `AtlasContext.recommendationInsights` → chat), but `calculateFeedbackConfidenceAdjustment`'s output never reaches `resolvePatternUpdate` — the two confidence mechanisms are deliberately decoupled per this milestone's "clean interfaces, no tight coupling" scope. Real future value, gated on enough accept/reject volume to design the coupling deliberately rather than guessing at its shape now. *Files: `lib/intelligence/recommendations/feedback.ts`, `lib/intelligence/personalDNA/confidence.ts`.*
- **No active `expired` sweep for stale `recommendation_events`.** The status is fully modeled (feedback weight, valid-transition rule) but nothing marks a long-`pending` suggestion `expired` — needs a scheduled job, which doesn't exist yet (see Future Vision below). Suggestions that sit unanswered currently just stay `pending` forever rather than eventually contributing their (weak, per design) negative signal. Now also applies to Goals Experience v2's `goal_next_action` and Learning Experience v2's `learning_next_review` events, both of which — unlike calendar suggestions — are explicitly designed to persist as the same `pending` row across repeat page views until acted on, so this gap is more visible there, not new.
- **Migration `20260720000006` (knowledge_entries study fields) has not been applied to the live database.** Written and typed against (`types/database.ts`), covered by the code that reads/writes the new columns, but this environment has no outbound network access to Supabase (confirmed during Timeline and Goals verification — DNS resolution to the project host fails), so `npm run db:migrate` couldn't be run here. Needs running from an environment with real network access before Learning Experience v2's study-streak/flashcard features work against production data. *Files: `supabase/migrations/20260720000006_knowledge_entries_study_fields.sql`.*
- **Calendar suggestion ranking doesn't consult recommendation feedback.** Same "foundation, not rebuild" scope as the Personal DNA calendar integration above — `recommendationInsights` reaches chat's context but not the suggestions route's own ranking logic. *Files: `app/api/calendar/suggestions/route.ts`.*
- **Atlas Intelligence Engine's recency dimension is flat (always 1.0).** Real per-item recency isn't recoverable at the `AtlasContext` boundary (fields arrive as already-formatted strings, not raw rows with timestamps) — the scoring formula keeps the term rather than hardcoding it away, but it currently contributes nothing to ranking. Not a bug, a documented v1 scope limit — see `docs/ATLAS_ARCHITECTURE_VISION.md` §9. *Files: `lib/intelligence/core/rank.ts`.*
- **Priority-conflict detection is competition-detection, not schedule-collision detection.** `detectPriorityConflicts` flags when top-ranked signals from competing categories (goal/relationship/upcomingEvent) coexist — it does not know whether a suggested time slot literally overlaps a real calendar event, since most signal types carry no structured time. Honest v1 scope, not a gap to silently work around. *Files: `lib/intelligence/core/conflicts.ts`.*
- **`buildIntelligenceSignals`/`rankSignals`/`detectPriorityConflicts` have no automated test against the DB-backed orchestration layers that feed them** (`buildAtlasContext`, etc.) — the pure engine itself is fully tested; what's untested is the same "no integration-test harness yet" gap as everything else DB-touching.
- **No score-history table exists, so Areas Experience v2's "recent progress" is a windowed activity-count proxy, not a true score trend.** `life_area_scores` only ever holds the current value — there's no way to say "your score was 55% two weeks ago." `lib/areas/computeActivityTrend.ts` compares logged-activity volume across two 14-day windows instead, a real and honest signal, but a different question than "is the score itself trending up or down." Revisit if a real feature need justifies a `life_area_score_history` table — not built speculatively ahead of one. *Files: `lib/areas/computeActivityTrend.ts`, `app/api/areas/insights/route.ts`.*
- **`/api/briefing` and `getInitialState()` (bootstrap) query overlapping tables independently** (life-area scores, goals, people, etc.) — `AIBriefing` fetches client-side on mount and calls `buildAtlasContext` fresh, rather than reusing bootstrap's already-fetched raw data, because the two need differently-shaped data (bootstrap needs raw entities to render lists; the Intelligence Engine needs `AtlasContext`'s pre-formatted strings). One extra round of duplicate queries per Today page load — real, small, not yet worth a shared per-request cache given "measure before optimizing." Revisit if it ever shows up in real latency numbers. *Files: `app/api/briefing/route.ts`, `app/actions/bootstrap.ts`.*
- **Experience Layer v1 (Today) + Timeline/Goals/Learning/Areas Experience v2 are done; Family Care and the generic `/areas/learning` page are still functional-but-plain.** Each is a task list or log, not a "journey" as the product vision frames it. Each was audited and explicitly deferred, not overlooked — see `docs/ATLAS_ARCHITECTURE_VISION.md` §10. *Files: `app/areas/family/page.tsx`, `app/areas/learning/page.tsx`.*
- **`Modal` has no focus trap or return-focus-on-close.** All three usages (`AICompanion`, `QuickCapture`, `OnboardingFlow`) close on Escape/backdrop-click but don't trap `Tab` within the open panel or restore focus to whatever triggered it once closed — a real gap against WCAG's modal-dialog guidance, deliberately not attempted blind (a focus trap implemented without a live browser to test against risks *breaking* keyboard nav worse than the current gap). *Files: `components/ui/Modal.tsx`.*
- **No skip-to-content link.** Low priority given `NavBar` currently has only 3 short links, but a keyboard user still has to tab through them on every page before reaching `<main>`.
- **No instrumented accessibility/performance audit (axe, Lighthouse) has been run.** The cross-app design/motion/a11y pass (`docs/ATLAS_ARCHITECTURE_VISION.md` §10) was grep-driven code review — real fixes landed (focus-visible indicators app-wide, `prefers-reduced-motion` support, under-sized touch targets, two motion/radius inconsistencies) — but nothing here was verified against a live authenticated session or real assistive tech, same standing gap as every other "needs a real Google sign-in" item in this document.

## Future Vision
*Large ideas, experimental features, long-term concepts.*

- A genuine unprompted "background AI" behavior — a scheduled job generating the daily insight, rather than the one hand-seeded example that exists today. Also the natural home for a `recommendation_events` `expired` sweep once it exists.
- **Adaptive ranking** — once real usage shows the Atlas Intelligence Engine's fixed 0.5/0.3/0.2 importance/confidence/recency weights (`docs/ATLAS_ARCHITECTURE_VISION.md` §9) under- or over-value a category in practice, revisit them against real data instead of the initial reasoned-but-untested split. Still deterministic, still explainable — "adaptive" here means "re-tuned periodically by a human looking at real outcomes," not a learned model.
- **Predictive prioritization** — feed `calculateFeedbackConfidenceAdjustment`'s signal (Recommendation Intelligence, §7) into the Intelligence Engine's ranking itself, and into Personal DNA's `resolvePatternUpdate` (§3), so a category with a strong accept/reject history actually shifts future ranking instead of only informing chat's context. Deliberately not built yet — needs real accept/reject volume to design the coupling against, not guess at it.
- **Decision engine v2** — real per-signal recency (once available at the `AtlasContext` boundary for a concrete reason) and genuine schedule-collision detection (once structured time data exists on more signal types) both graduate the current priority-*competition* detection into actual conflict *resolution*. Explicitly gated on both prerequisites being real, not built speculatively — see "Avoid: agent systems, complex automation engines, prediction models" in `docs/ATLAS_ARCHITECTURE_VISION.md` §9.
- **Adaptive UI** — the Today page's section order/emphasis shifting based on what's actually been useful to the user (e.g., a person who never acts on calendar suggestions but always engages with Goals sees Goals surface higher), once there's real interaction data to adapt from rather than a guess.
- **Predictive Home Screen** — Today anticipating what the user needs *before* they open the app (e.g., the briefing pre-computed and ready the moment a notification could be sent), which depends on real notification infrastructure and a scheduler that doesn't exist yet — same prerequisite gate as the recommendation-engine's own "predictive prioritization" entry above.
- **Ambient Intelligence** — Atlas surfacing something useful in contexts outside the app itself (a notification, an email digest, a calendar-native suggestion), once real delivery infrastructure exists. Explicitly not agent behavior or autonomous action — still deterministic, still requires the same explicit accept/reject the in-app feedback loop already models.
- Voice input for Quick Capture and Torah Space.
- Native mobile app, if usage data ever justifies it.
- Billing/plans — only once there's an actual reason to charge, not built speculatively.
- Multi-device presence/sync indicators.
